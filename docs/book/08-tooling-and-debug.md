# Chapter 8: Tooling And Debugging

EZC has a small runtime, so tooling can stay direct.
Use the pipeline views aggressively when diagnosing behavior.

## 8.1 Parse And Compile Validation

Use `check` to validate a source file without execution.

```bash
cargo run -- check demo/fib.ezc
```

If parsing or compilation fails, EZC reports structured diagnostics with source spans.

## 8.2 Disassembly

Inspect generated bytecode and spans:

```bash
cargo run -- disasm demo/gcd.ezc
```

This is the fastest way to confirm that your words mapped to the intended opcodes.

## 8.3 Verbose Runtime Trace

Use `--verbose` on commands that execute code.

```bash
cargo run -- --verbose run demo/triangular.ezc
```

Verbose mode includes stage-level debug output so you can trace value flow.

## 8.4 REPL Workflow

Terminal REPL (`cargo run -- repl`) is best for micro-iteration:

- test one stack transform
- test one condition
- test one loop step
- merge into full block

Web REPL (`/repl`) gives the same persistent stack model with completion hints.

## 8.5 Minimal Repro Discipline

When something is wrong, shrink input until only the failing transform remains.

```ezc run
3 4 + 5 *
```

Then rebuild one word at a time.

## 8.6 Debug Checklist

1. Is the stack shape what the next operator expects?
2. Are you accidentally consuming a value with `prt` or `del`?
3. Does a `^` block always leave a condition value?
4. Are symbolic data values accidentally used as executable words?

Keep this loop tight and EZC bugs become easy to isolate.
